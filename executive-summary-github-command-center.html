Executive summary · GitHub Command Center

Every feature is built. Nothing is committed to.

A single HTML file that lets one person run two GitHub accounts from one PC without pushing work to the wrong account and without committing a credential. Every capability in the original brief is built and working. What is missing is everything around it: the file has no version history, the tests that proved the guards work were deleted after running, and nothing has yet been run against a real GitHub account.

01 · Target

What this project is for.

The outcome in one sentence, then the boundary. The boundary is what stops the next person expanding the scope by assumption.

Outcome

One person, two GitHub accounts, one PC

The owner can push to a personal and a work account from the same machine, always to the right one, and can stop a credential from ever reaching a remote. The app teaches the commands, generates the hooks, and the owner's own terminal does the enforcing.

Out of scope

What this deliberately is not

Not a Git client — a browser cannot touch the filesystem or intercept a commit, so every guard is a script the user installs and runs. Not a sync service, not multi-user, not a replacement for GitHub Desktop. Exactly two accounts are modelled, and the app makes no network requests at all.

Two accounts that cannot be confused

Shipped

A commit with a credential in it is cancelled

The pre-commit hook exits non-zero, names the offending file, and names the rule that matched. The commit does not happen; nothing is written to history.

index.html · shellHook (line 955)

Shipped

A push that would upload a secret is cancelled

The pre-push hook rebuilds the range git is about to send and diffs every commit in it, added lines only. A secret added and then deleted inside the same push is still caught, because that commit is still in what would be uploaded.

Shipped

Secrets already in history can be found and rotated

The history scanner walks every reachable blob and produces a ranked revoke checklist with provider-specific instructions. Values are masked in the report, so the report is not a second copy of the problem.

Partial

A vault with no plaintext at rest

Entries are encrypted with AES-256-GCM under a key stretched through 600,000 PBKDF2 rounds, and the master password is never stored. The gap: the key exists only in memory while unlocked, so closing the tab ends the session, and a forgotten master password means the vault is unrecoverable by anyone.

05 · Feedback

How the project actually is.

The read you would give in a meeting: what is genuinely strong, and what is genuinely weak. A feedback section with no weakness in it gets the whole page discounted.

Working well

The guards are proven, not asserted

122 assertions were run against the generated hooks on real repositories with a bare remote, in both the shell and Node engines. That testing found four silent no-ops, including a bulk installer that reported success while writing hook files git would never execute, and a dry run that quietly rewrote repository config. Finding those is worth more than the features that were never in doubt.

Needs work

4,033 lines in one file, with no seams

One file holds 12 views, two hook generators, four scanners, an encrypted vault, routing, a print sheet and the router. There is nowhere to put a change that affects one concern without touching the whole file, and no test to catch a regression. It is also why the same bug had to be fixed twice during the last piece of work: the shell and Node guards duplicate their logic and share none of it.

Risk

There is no version control anywhere in this project

The folder is not a git repository, so the entire deliverable is one untracked 241KB file with no history, no diff and no rollback. This is invisible in the code and it is the largest risk on the page: one bad edit, or one truncated write from a tool, is unrecoverable. The project that exists to teach safe Git practice and prevent credential leaks is itself held together by a single unversioned file, which is worth naming plainly rather than leaving for someone to discover.

The honest caveat.

Nothing in this project has been run against github.com or against a real two-account Windows machine. Every guard was proven against purpose-built local repositories with a bare remote, which exercises the hook logic properly but says nothing about the account routing, the credential helper, or the SSH key generation. Those are generated text that has never been executed end to end, and a reader should assume they will need adjustment on first contact with the real machine.

06 · Focus

One thing to do next.

Not a list. If two things are equally urgent, the page has not made a decision yet.

Put the file under version control before anything else changes.

A reader would reasonably pick "test it on the real machine" instead, and it is the more interesting job. Version control wins because it takes minutes and makes every subsequent fix reversible, including the fixes that testing will certainly produce.
